Almost every radio firmware out there is written in C. Ferrite isn't. I picked Rust before a single line of Ferrite
ran on the radio, and it's shaped almost everything since. Here's why.

## A radio is a computer with a transmitter bolted on

The RT-950 Pro has a 240 MHz ARM Cortex-M4 (Ferrite runs it at up to 120 MHz), 96 KB of RAM and two radio chips.
The firmware decides what frequency the transmitter keys up on, at what power, and for how long. When that code is
wrong, you don't get a crash on a screen. You get a carrier on the wrong frequency.

So I wanted the strictest checks I could get, and I wanted them early. Rust's compiler refuses whole classes of
mistakes before the code ever gets near the radio: using memory after it's gone, two tasks changing the same thing
at once, a case the code forgot to handle. Every one of those is a bug I never had to chase on the bench.

## The bench is the slow part

Changing radio firmware means building an image, flashing it over the programming cable, then testing it on a real
radio with a real signal. That's minutes, every time. A bug the compiler catches costs seconds.

I build Ferrite with AI tools helping, and Rust's compiler is a tough reviewer for every line, mine or not. If it
compiles, a lot of things are already true.

## I measured the cost first

My first test image for the radio was in C, the usual way. Before going any further, I ported it to Rust, feature
for feature, to see what it would cost. The Rust version came out about a third bigger. That's real, and we watch
size closely: part of the chip's flash is fast and part is slow, and anything that runs often has to fit in the
fast part. But the radio has room, and the checks are worth way more to me than the bytes.

## Same code on the radio and on a computer

Everything above the hardware is plain Rust that builds for a PC as well as for the radio: the screens, the menus,
the APRS decoder, the channel storage, the link to Ferrite Console. That pays off every day:

- **Thousands of tests run on a computer** in seconds, on every change, before anything gets flashed.
- **The screen recordings on this site** are the firmware's own drawing code, running on a PC.
- **Ferrite Console** uses the radio's own code, compiled for the browser, to read and write your channels, so the
  two can't drift apart.

## No surprises halfway through a transmission

Ferrite never grabs memory while it runs. Everything has its place when the firmware is built, so it can't run out
mid key-up. The code that pokes the hardware directly lives in one small, fenced-off corner, and each piece of it
says why it's safe. If something does go wrong anyway, the radio stops transmitting and goes to a safe state
instead of carrying on.

## Waiting costs almost nothing

Ferrite runs on [Embassy](https://embassy.dev), a Rust framework for small processors. Each job (the radio, the
screen, the keys, APRS, GPS) is its own task that sleeps until it has work to do, and while everything's asleep,
Ferrite drops the processor right down to 24 MHz. Sitting on a quiet channel, the radio draws about 19 mA. That's
about 107 hours on the stock battery pack.
